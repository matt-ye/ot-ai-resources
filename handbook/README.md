## Chat 與 Agent：會說和會做

**定義**

- **Chat**：你問，它答，答完就結束。你拿到的是一段話。
- **Agent**：你交代一件事，它自己排步驟、用工具、讀寫檔案、檢查結果，最後留下檔案與紀錄。

**門診諮詢 vs 療程**

| | Chat | Agent |
|---|---|---|
| 比喻 | 門診諮詢：你描述狀況，專家給建議 | 把整個療程跑完：評估、計畫、介入、再評估 |
| 你拿到什麼 | 一段回答 | 一串可以打開來看的檔案 |
| 事後能不能回頭查 | 要自己重建它做了什麼 | 每一步都有紀錄 |

兩者最關鍵的差別，是 Agent 每一步都留有紀錄，事後能打開檔案查驗過程。如果沒有留下紀錄，只是「做得比較多」，就談不上 Agent 的優勢。

**講座裡的例子：Agent 做了哪些 Chat 做不到的事**

- 文獻雷達：每個月自己去 Europe PMC 查新論文，去掉重複的，請 AI 初篩，再開成一張 GitHub 上的工作單（Issue），並且留下「篩掉了哪些」的紀錄。這是「自己定期去做」，Chat 要等你開口才動。
- 大量萃取：近千篇論文交給 AI 依固定欄位萃取，存成檔案，再用另一條不同提示的管線，從統計結果互相比對方向。這是「讀寫檔案、批次處理、檢查結果」。

**Agent 不是全自動。** 題目、納入哪些文獻、最後的確認，仍然是人。Agent 負責中間跑腿的那一大段。

**灰色地帶**：現在的聊天介面也常接了搜尋或檔案功能，兩者是光譜，沒有乾淨的界線。本手冊的判準是兩個問題：它能不能自己規劃多個步驟？它做完有沒有留下可以回頭查的檔案？兩個都有，就叫 Agent。這是教學用的劃分，不是業界公認的分類。

## 四種連接方式：API、MCP、Skill、CLI

AI 本身只會產出文字。要查資料、讀檔、寫檔，需要接上外面的東西。常見有四種接法。

| 連接方式 | 一句定義 | 比喻 | OT 情境例子 | 在講座哪裡出現 |
|---|---|---|---|---|
| **API** | 讓程式（不用人坐在聊天視窗前）直接呼叫模型或資料庫 | 機構之間的專線電話 | 每個月自動去 Europe PMC 查「中風上肢任務導向訓練」的新文獻，不需要有人開網頁 | 文獻雷達呼叫 Europe PMC 與篩選模型 |
| **MCP** | 一套標準格式，讓 AI 工具用同一種方式接上 PubMed、Zotero 這類工具 | 標準化轉介單：同一張單，可轉給不同單位 | 同一個 AI 助手先查 PubMed，再把結果存進 Zotero，不必為每個工具各學一套 | 第 7 章的 PubMed 操作（講座不展開） |
| **Skill** | 寫成文字檔的作業手冊，平常只放目錄，需要時才讀全文 | 科內的作業手冊 | 「中風個案上肢評估報告的格式與必填欄位」「個案討論會簡報整理步驟」 | 講座未示範 |
| **CLI** | 用文字指令操作電腦，讓 AI 直接讀寫檔案、批次處理 | 直接進治療室動手 | 把一個資料夾裡的 40 份虛構治療紀錄整理成一張表 | 把萃取結果寫成知識卡、存進知識庫 |

**Skill 與常駐規則檔的差別**：常駐規則檔像貼在桌上的基本守則，AI 每次開始工作都會整份先讀，適合放底線與通則。Skill 像書架上的作業手冊，平常只看目錄（名稱與一句說明），需要時才翻開讀全文，適合放很長的流程。

**對照講座的自動化專案**：講座示範的是「用 API 來源自動檢索，再大量萃取，最後寫進知識庫」。查文獻靠 API（Europe PMC）；大量萃取靠 CLI 呼叫模型（也可以走 API）；統計彙整與比對是一般的小程式；寫知識卡靠 CLI。第 7 章的 PubMed 查詢是 MCP 的操作例子，講座不展開，放在手冊讓你課後自己練。

## 資料分級與安全

**聲明**：本章是一般原則，不是法律意見。研究資料以 IRB 與研究倫理中心的意見為準。學校《生成式 AI 使用與研究誠信指引》原文編者尚未讀過，這裡不引條文，請參考學校指引。

**三級分流**

| 等級 | 職能治療情境的例子 | 可以交給誰 |
|---|---|---|
| 公開 | 已發表文獻、公開課程 | 任何雲端 AI |
| 內部 | 自編教材、已去識別的統計表、行政文件 | 機構或商業方案（預設不拿資料訓練） |
| 敏感 | 病歷與評估紀錄、學生成績與作業、未發表研究、IRB 資料 | 只能用本機模型 |

**原則：不確定屬於哪一級，就當敏感處理。** 不要自己降級。上表的「只能用本機模型」是指原始的敏感資料；若真的需要大模型，只能走下面「七條」的做法，先在本機去識別化並由人抽查，再交給機構簽約的方案，不能直接上傳原始資料。常見的灰區：學生的匿名評量意見（自由文字常寫到特定老師或事件）、罕見診斷加特殊年齡的個案摘要、某一格人數只有 1 到 2 人的統計表。

**公開不等於可以任意再散布**：已發表的文獻可以交給雲端 AI 讀，但全文授權各不相同，先查授權。

**五條檢核清單，每條怎麼做**

| 條 | 內容 | 怎麼做 |
|---|---|---|
| 1 | 先分級 | 把手邊的資料夾各貼一個等級。評估紀錄、實習評量是敏感；已發表文獻是公開 |
| 2 | 確認真的在本機執行 | 先看軟體設定與模型名稱（名稱帶 cloud 的在雲端跑）；再拔掉網路跑一次，看能不能正常運作；如果用的是 Ollama，可以在命令列輸入 `ollama ps`，確認模型載在本機（第 5 章說明本機與雲端的差別）。處理真資料之前，先拿虛構資料試跑 |
| 3 | 上雲前去識別化並抽查 | 先在本機遮掉姓名、病歷號、生日、學號，日期改成相對時間；由人抽查 |
| 4 | 雲端只用機構或商業方案 | 請學校或機構簽約；個人消費版不適合處理敏感資料 |
| 5 | 研究資料先洽 IRB 與研究倫理中心 | 計畫書與同意書寫明用哪個 AI 工具、資料傳到哪裡、怎麼保存 |

**敏感資料若需要用大模型：七條**

不鼓勵直接上傳。真的需要時，以下是把風險降到最低的一般原則（與上面的五條檢核清單相輔相成，其中部分重點會重複出現，是刻意的提醒）。

1. **先問能不能不用原始資料。** 只送完成任務所需的最少欄位；能用彙總統計、表格結構或虛構範例代替的，就不送原始紀錄。
2. **送出前在本機去識別化，並由人抽查。** 移除姓名、病歷號、生日、學號、地址等直接識別資訊，日期改成相對時間，罕見診斷與年齡合併分組。去識別化後若仍可能被還原身分，依法仍可能屬於個人資料。
3. **拆分任務，本機與雲端分工。** 識別資訊的抽取、遮蔽與比對交給本機模型；去識別後的推理、摘要與寫作才交給大模型。
4. **只用機構簽約的商業或教育方案。** 確認合約寫明不拿輸入資料訓練、資料保留期限，必要時申請零資料保留。消費版即使關閉訓練開關，也不適合處理敏感資料。
5. **研究資料先取得同意與核准。** 在 IRB 計畫書與受試者同意書寫明使用的 AI 工具、資料傳輸地點與保存方式，並先洽研究倫理中心。
6. **留下紀錄。** 記錄送出了哪些資料、用了哪個服務、何時刪除，以便稽核與回應當事人查詢。
7. **長期需求考慮機構自建。** 由學校或系所在受控環境部署開放權重的大模型，資料不出校園。進階硬體（顯示卡記憶體 24GB 以上）可執行 270 億到 350 億參數等級的模型（數字越大，模型通常越強、也越吃硬體），可請計資中心協助評估。

## 本機模型：能做與不能做

本機模型指跑在自己電腦裡的 AI。優點是資料不必離開電腦。以下結論是講者在自己電腦上的小樣本實測，只代表這次、這台機器、這些任務，不是通則；結果會隨電腦規格與資料型態而異，請用自己的資料另外測。

**實測結論（含條件與樣本數）**

| 任務 | 結果 | 條件與樣本數 |
|---|---|---|
| 從格式清楚的虛構評估紀錄抽取欄位 | 12 次全對，單次約 5 秒 | 2 個 80 億參數模型，各 3 次，再加上拿掉兩句提醒的對照組各 3 次，共 12 次。資料是虛構個案 |
| 從凌亂的臨床速記抽取欄位 | 不穩：其中一個欄位 6 次錯 4 次，多半填成四週前的舊分數 | 2 個模型各 3 次。就算提示補上「本次」，其中一個模型仍然錯 |
| 對可疑欄位「只再問一次」 | 原本 5 次全錯，重問後 5 次都改對 | 1 個模型，5 次，凌亂版虛構紀錄 |
| 讓本機模型自己規劃多步驟（找檔、讀檔、回答） | 本機 80 億參數模型約 200 秒、答錯；雲端 1,200 億參數的免費模型約 20 秒、全對 | 各測 1 次，送上雲端的是講者自己寫的、不含病人或學生資料的卡片 |

**怎麼讀這張表**

- 這 12 次「格式清楚、有標準答案、單次」的虛構紀錄抽取，兩個本機模型都答對。分類與短摘要沒有測，要自己試。
- 多步驟 Agent 任務只各測 1 次：本機模型約 200 秒、答錯，雲端模型約 20 秒、全對。次數太少，不能據此說本機模型一定不行，但要拿它跑 Agent，得先自己測。
- 凌亂紀錄的錯誤，答案看起來仍然完整，光看不一定發現。所以要有標準答案可以對，並用程式檢查格式與範圍。

**「拔網路」證明了什麼**

拔網路後還能跑完，只能確認「這一次 AI 運算產生回答（稱為推論，與研究方法的統計推論不同）時不需要網路」。它不單獨證明資料沒有離開電腦，也不保證軟體在其他時候不會在背景連出去。要和「看模型實際載在哪裡」「確認程式連的是本機」合起來看，才算有證據。

**用本機工具，不等於資料留在本機**

- 有些本機軟體的選單裡也放了雲端模型的選項，畫面一樣、按鈕一樣，點下去資料就出去了。例如 Ollama 名稱帶 cloud 的模型，是在 ollama.com 上推論，須登入 ollama.com（官方說明：https://ollama.com/blog/cloud-models，2026-10-21 核對）。
- 有些 Agent 工具會自動挑選供應商，設定放在那裡，不一定啟用，但要檢查。
- 同一個工具，改一行設定就能改接雲端。

所以不要憑軟體名字猜，看設定、看模型載在哪、拔網路再實測一次。

**硬體入門**

- 本機模型最吃的是**顯示卡自己的記憶體（簡稱 VRAM）**。模型塞得進顯示卡記憶體才跑得快。
- 講者的筆電顯示卡記憶體為 8GB，80 億參數等級的模型是甜蜜點，約每秒 40 個字詞。
- 模型超過顯示卡記憶體容量時，軟體通常不會跳出錯誤訊息，只會悄悄變慢。實測中，把單次可處理的文字量上限（模型長度需求）調高後，速度從每秒四、五十個字詞掉到約 8 個。
- 規格寫 8GB，實際可用大約 6GB，因為桌面與瀏覽器會佔用。
- 更大的模型（例如 24GB 顯示卡記憶體以上跑 270 億至 350 億參數）是規劃方向，未實測。

**軟體入門**：Ollama 與 LM Studio 是常見的本機模型工具（LM Studio 有圖形介面，較容易上手）。軟體版本與功能變動快，安裝前請看官方說明。

**月費**：各訂閱方案與價格變動快，本手冊不列，請以各官方頁為準。

## 自動檢索：不寫程式也能開始

**最簡單的起點：PubMed 的 Create alert**

PubMed 搜尋框下按「Create alert」，可以設定 email 自動通知，需登入 My NCBI。官方說明：https://pubmed.ncbi.nlm.nih.gov/help/

步驟：

1. 登入或註冊 My NCBI（網址見第 9 章 PubMed 列）。
2. 在 PubMed 搜尋框輸入英文關鍵字（PubMed 以英文檢索），例如中風、上肢、任務導向訓練的英文詞，中間用 AND 連接。
3. 先看結果對不對，不對就調整關鍵字。
4. 按搜尋框下的「Create alert」，選通知頻率。
5. 之後新論文會寄到你的信箱，不用記得去查。

**免費學術 API（進階）**

想讓程式替你查，這些服務都有免費用法：

| 服務 | 用途 | 網址 |
|---|---|---|
| Europe PMC | 歐洲生醫文獻與開放全文，免金鑰。講座的文獻雷達用的就是它 | https://europepmc.org/RestfulWebService |
| Crossref | DOI 與書目資料，請求加上 email 進入禮貌池 | https://api.crossref.org |
| Unpaywall | 用 DOI 找合法的開放全文 | https://unpaywall.org/products/api |
| OpenAlex | 全領域學術圖譜 | https://openalex.org/signup |
| ClinicalTrials.gov API v2 | 查詢臨床試驗登記，免金鑰 | https://clinicaltrials.gov/data-api/api |

額度、申請步驟與注意事項見第 9 章。

**講座的文獻雷達**：五步是排程、檢索、去重、AI 篩選、開成一張工作單。AI 只負責篩選，不寫摘要；被篩掉的收在摺疊區，人可以檢查；AI 全部失敗時，報告會明寫這次篩選失敗、內容未經過濾。想換成自己的主題，只需要改一個設定檔（搜尋主題）和一段判準（收案與排除條件），程式不用動。

文獻雷達是靠 GitHub Actions（GitHub 的雲端自動排程功能）定期執行。對公開 repo（公開的專案資料夾），使用標準 GitHub 代管 runner（GitHub 提供的雲端執行主機）免費；大型 runner 一律收費（官方說明：https://docs.github.com/en/billing/managing-billing-for-github-actions/about-billing-for-github-actions）。

**文獻雷達通用版**：放在本 repo 的 `1-literature-radar/`，關鍵字設定檔有範例，照著 README 就能開始。

**限制要知道**：雷達只適合持續追蹤新發表的論文，不等於系統性回顧的完整檢索（查詢範圍窄、每主題只看前幾篇）。做系統性回顧仍要用完整檢索策略與多資料庫。

## PubMed MCP 操作步驟

目的：讓 AI 工具真的去 PubMed 查，每一篇都帶編號（PMID），可以拿去核對，而不是 AI 憑記憶湊出來的清單。

**事前準備**：在你使用的 AI 工具（講座用的是 Claude Code）接上 PubMed 的 MCP 連接器，並確認狀態為已連線。連接器名稱與安裝方式會因工具版本不同，本手冊不寫安裝指令，請依該工具的官方說明，或請用過的同學、老師帶你做一次；MCP 概念可看官方頁 https://modelcontextprotocol.io/。

**步驟一：提問一（搜尋）**

貼上類似下面的提問（可換成你的主題）：

> 請用 PubMed 查 2024 年以後發表的隨機對照試驗。條件：成人中風、上肢的任務導向訓練、以 Fugl-Meyer 上肢量表為結果。列出 5 篇，每篇一行：PMID、第一作者、年份、期刊。

等待 1 到 2 分鐘。重點看每一篇是否都有 PMID。

**步驟二：提問二（指定一篇，查完整資料與授權）**

> 請查 PMID 38968539 的完整作者名單、DOI 和授權條款。

**步驟三：回原始資料核對（最重要的一步）**

AI 給的引用，一律回 PubMed 原始頁面核對。在 PubMed 輸入該 PMID 打開原頁，逐項對照：

1. PMID 打得開嗎？
2. 作者名單與順序一致嗎？
3. DOI 一致嗎？
4. 年份與期刊一致嗎？
5. 授權條款與期刊頁面一致嗎？

有一個字不一樣，就以 PubMed 為準。

**步驟四：用全文之前先查授權**

要把全文交給 AI 或投影之前，逐篇確認授權與用途。講座用的 5 篇都是開放取用，授權為 CC BY-NC 或 CC BY-NC-ND，允許非商業教學（2026-10-19 查證）。全文只存在講者電腦、不散布；萃取示範時，裁切後的全文交給雲端模型處理，所以只選用允許教學使用的開放取用論文。

**如果出錯**：搜尋結果沒有你要的那篇，就直接指定 PMID（提問二）；回覆與原頁不一致時，以 PubMed 為準，這正是要回原始資料的理由。

**金鑰保管五原則**

金鑰就像診間藥櫃的鑰匙：不貼在牆上、不同櫃用不同把、遺失立即換鎖。

1. 不貼進程式碼、文件、聊天、截圖或公開分享的雲端文件。
2. 存在密碼管理器（或電腦系統供程式讀取的「環境變數」設定），不要存成桌面上的文字檔。
3. 不同用途、不同專案各用一把，方便單獨撤銷。
4. 疑似外洩時，立即到該服務後台撤銷並重建。
5. 定期查看用量頁，用量異常增加就更換金鑰；能設到期日與最小權限的都要設。
