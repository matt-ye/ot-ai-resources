# ⑥ 迭代：把失敗寫成規則，再回到規劃

> 授權：程式 MIT、文件 CC BY-NC 4.0。

## 這是什麼

大量萃取一定會出事。差別在於：出事之後，是「修好就算了」，還是「寫成一條規則，下次開工前就檢查」。這一階段是第六階段的核心：**每個失敗，都要留下一條能被檢查的規則，並回寫到 `01_plan/` 的說明書**。

## 你需要先準備什麼

- 出事當下的簡單記錄（日期、看到什麼）。不用漂亮，但要在記憶還新的時候寫。
- `失敗寫成規則_模板.md`。

## 檔案

| 檔案 | 用途 |
|---|---|
| `失敗與返工時間序.md` | 原專案的失敗與返工（匿名改寫）：發生什麼、怎麼處置、留下什麼規則 |
| `失敗寫成規則_模板.md` | 把一次失敗寫成規則的五欄模板，附一個填好的例子 |
| `聚合統計.md` | 原專案的聚合數字（漏斗、語料組成、方法學比例），每個數字標分母與口徑 |

## 逐步 SOP

1. **（人★）出事就先記下來。** 在哪裡做：專案資料夾裡的 `失敗記錄.md`（自己建）。寫：日期、你看到的現象（不要寫猜測的原因）。
2. **（人★）查原因。** 區分「現象」與「原因」。原因要有證據，例如「看了 10 筆輸出，其中 9 筆是同一種錯」。查不出來就寫「原因未確認」。
3. **（LLM＋人★）寫成規則草稿。** 在哪裡做：LLM 對話。貼上：「這是我們的失敗記錄（貼上）。請用 `失敗寫成規則_模板.md` 的五欄格式寫成規則草稿；原因不確定的寫『未確認』；『怎麼檢查』要寫成可以被執行的檢查，不要寫『要小心』。」為什麼：LLM 擅長整理格式，但**原因與檢查方式要人確認**。
4. **（人★）核准規則。** 你確認它真的能防止同樣的事再發生。
5. **（人★）寫回規劃。** 把規則加到說明書的「紅線」「停止條件」或「驗收標準」，並在說明書「日期化補充」裡記一筆。
6. 下一輪開工前，把規則清單當成開工檢查表跑一遍。

## 哪裡用 LLM、哪裡一定要人

- LLM：整理記錄、起草規則。
- 人★：確認原因、核准規則、寫回說明書。

## 限制

- 原專案的失敗記錄是事後整理的，日期只填來源有標示的，其餘寫「未標」。
- 聚合統計來自講者專案，是已發表論文的倖存者樣本；數字用來看方向與預設值，不是「應該怎麼做」的證明。
